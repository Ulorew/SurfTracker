# Телефон: сверка, скорость, тепло, камера

Устройство: **Redmi Note 14 Pro 5G** (24090RA29G), Android 14 / SDK 34,
HyperOS OS1.0.10.0, **MT6878 (Dimensity 7300-Ultra)**, 4×A78 2.5 ГГц +
4×A55 2.0 ГГц, arm64-v8a.

Инструменты: adb 37.0.1, JDK 21, SDK build-tools 35 — локально, без sudo.
Gradle не использован: APK собирается четырьмя вызовами (aapt2, javac, d8,
apksigner). Весь вывод — json и файлы.

## 0. Разведка

| | значение |
|---|---|
| INFO_SUPPORTED_HARDWARE_LEVEL | **LEVEL_3** (обе камеры) |
| макс YUV_420_888 (тыл) | **4080×3060** |
| getOutputStallDuration на нём | **0 нс** |
| мин. длительность кадра | 33.3 мс (потолок 30 fps) |
| обязательных комбинаций потоков | 62 |

**LEVEL_3 подтверждён устройством** — дыра ресёрча («по Notebookcheck, не
подтверждён») закрыта. Нулевой stall означает, что полноразмерный YUV не
тормозит остальные потоки.

## 1. Сверка инференса — сходится

Заявленный тикетом допуск 1e-5 обоснован тем, что «интерпретатор тот же».
**Посылка неверна:** на ноутбуке x86-64 и на телефоне arm64 работают разные
сборки с разными ядрами XNNPACK. Проверено замером, а не рассуждением:
входной тензор на телефоне совпал с ноутбучным побитово (px0 = ff98a3a9 =
RGB(152,163,169); сумма 1.2 млн значений 702964.31 против 702964.38 —
разница порядка накопления), а выходы разошлись на 2e-3.

По существу модель считает то же. После NMS — то, что получает трекер:

| | |
|---|---|
| рамок сопоставлено по IoU | 63, без пары 0 |
| разница в числе рамок | 0 |
| худшее смещение центра | **17.3 px из 640 = 6.2% размера рамки** |
| худшее расхождение уверенности | 0.020 |

Добавлен режим `phone_pack.py compare-nms` с допуском в долях размера рамки
(10% — вшестеро строже критерия «та же цель» самого трекера).

## 2. Скорость

APK, не adb-бинарь. 30 прогревочных + 200 замеряемых, чистый `interp.run()`.

| модель | потоки | p50 | p95 | min |
|---|---|---|---|---|
| **w8a32** | **1** | **135.4** | **142.9** | 133.3 |
| w8a32 | 2 | 138.7 | 143.6 | 133.8 |
| w8a32 | 4 | 141.6 | 152.3 | 135.1 |
| w8a32, закреплён на A78 | 1 | 135.4 | 141.2 | 133.3 |
| fp32 | 1 | 231.2 | 240.5 | 225.6 |

**Потоки не дают ничего**, и это проверено на уровне механизма, а не
предположено: XNNPACK создаёт 4 потока, но один несёт 95.5% CPU, остальные три
по 5.8% — граф не распараллеливается. Закрепление на больших ядрах (маска f0,
cpu4-7) не меняет ничего; процесс и так в cpuset `/top-app`.

**fp32 вдвое медленнее w8a32** — выбор квантованной сборки оправдан не только
размером (3.0 МБ против 10.6), но и скоростью.

Бюджет: такт 3 Гц = 333 мс. p95 143 мс — **приемлемо** (≤150), до комфорта
(≤100) не дотягивает. GPU-делегат не пробовался, NNAPI не трогался.

## 3. Тепло

15 минут непрерывного инференса, 1 поток, экран включён, **питание по USB**
(не от батареи — условие записано), заряд 90% → 89%.

| минута | p50 | p95 |
|---|---|---|
| 1 (прогрев, не в отчёт) | 138.5 | 185.2 |
| 2–9 | ~184 | ~189 |
| 10 | 189.2 | 218.6 |
| 11–14 | ~215 | ~221 |

**Деградация 138 → 215 мс, в 1.55 раза от холодного старта** (1.17× от
установившегося уровня второй минуты). Установившийся p95 ≈ 221 мс — это
**вне «приемлемо» (150)**, но втрое ниже такта 333 мс.

`getThermalHeadroom(60)`: 434 замера, **NaN ни одного** (MediaTek отдаёт),
медиана по минутам 0.76 → 0.80, семь значений выше 1.0 — все в первые 13
секунд (артефакт холодного старта).

**`getCurrentThermalStatus` всё время 0** (троттлинга нет) при падении
скорости в полтора раза. Как сигнал для приложения он бесполезен — частота
падает без объявленного теплового события.

## 4. Камера

### 4а. Кандидаты — все пять поддержаны

`isSessionConfigurationSupported` на открытой камере (на API 34 проверка живёт
на `CameraDevice`, `CameraDeviceSetup` только с API 35):

| комбинация | вердикт |
|---|---|
| PRIV 1080p + PRIV 4K + YUV 1080p | поддержано |
| PRIV 1080p + PRIV 4K + YUV max | **поддержано** |
| PRIV 4K + YUV max (без превью) | поддержано |
| PRIV 1080p + YUV max (без записи) | поддержано |
| PRIV 1080p + PRIV 4K + JPEG 4K | поддержано |

### 4б. Практический прогон — частично, есть открытый вопрос

Пока запись идёт, потоки держат:

| YUV-поток | фактический fps | медианный интервал |
|---|---|---|
| 4080×3060 | **21.0** | 33.8 мс |
| 1920×1080 | **28.0** | 33.3 мс |

**Но сама запись обрывается примерно на 9-й секунде**, и вместе с ней встаёт
весь конвейер. `MediaRecorder` отдаёт `what=268436456` (статус завершения
видеодорожки) `extra=-1011`. Воспроизводится одинаково: при заданных руками
3840×2160 @ 40 Мбит/с и при параметрах из `CamcorderProfile.QUALITY_2160P`
(3840×2160 @30, 50 Мбит/с).

Проверено, что дело НЕ в YUV-потоке: контрольные прогоны без него и с
YUV 1080p обрываются так же (~9 с из 30 и из 60). Проверено, что дело не в
гашении экрана. Причина не установлена — это единственный незакрытый пункт.

### 4в. Путь снимков — не измерен

Зависит от 4б: считать пропуски кадров записи бессмысленно, пока запись сама
обрывается.

## Итоговая строка

**Телефон держит 3 Гц инференса с запасом: p95 143 мс на холодную и 221 мс
после 15 минут прогрева против такта 333 мс.** Многопоточность не помогает
(граф не распараллеливается), закрепление на больших ядрах тоже; квантованная
сборка вдвое быстрее fp32.

**4K-анализ доступен: LEVEL_3, все пять комбинаций поддержаны, YUV 4080×3060
идёт 21 fps параллельно с записью, stall 0 нс.** Оговорка: измерено на
отрезках до девяти секунд — дольше запись в моём тестовом приложении не живёт,
и до выяснения причины утверждение о длительной работе не подтверждено.
