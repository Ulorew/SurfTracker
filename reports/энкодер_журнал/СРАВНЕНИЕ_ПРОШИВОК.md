# Старая прошивка против новой: что изменилось и чем рискуем

21 августа 2026. Сравнение `phone_link.ino` из коммита `4b9dd8d` (лежит на
плате) с текущим деревом. Новая **не залита**.

Размер: 45 560 → 46 316 байт, то есть +756 байт, 35% флеша из 131 072.

---

## 1. Что изменилось в БОЕВОМ пути

Боевой путь — приём уставки, закон управления, телеметрия, питание фаз. Всё,
что телефон видит и чем вал управляется.

### 1.1. Приём кадров: ищется два магика вместо одного

```diff
-  if (rxn == 0 && b != proto::MAGIC_REQ) continue;
+  if (rxn == 0 && !isFrameStart(b)) continue;      // REQ или CMD
-  while (rxn > 0 && rxbuf[0] != proto::MAGIC_REQ) {
+  while (rxn > 0 && !isFrameStart(rxbuf[0])) {
```

**Риск, который надо назвать честно:** байт `0xC3` может встретиться внутри
полей боевого пакета — в мантиссе float скорости он вполне вероятен. Тогда
приёмник начнёт копить кадр с середины предыдущего.

Почему это не ломает связь: длина CMD равна длине REQ, а CRC-8 отбракует
случайную комбинацию с вероятностью 255/256. Отбракованный кадр уходит в
`rxShift()`, который сдвигает на байт и ищет следующее начало — механизм
ресинхронизации тот же, что работал и раньше при потере байта. Плата теряет
один кадр из тех, где так совпало, и восстанавливается на следующем.

Цена: телефон шлёт уставки 10 раз в секунду, кадр теряется незаметно —
`C.accept` просто не вызывается, а предыдущая уставка живёт до сторожа.

### 1.2. Питание фаз: два несвязанных управления сведены в одно

Это **исправление дефекта, внесённого стендом же**, и оно затрагивает боевой
путь.

```diff
-  static bool motor_on = true;
-  bool want_on = (millis() - nonzero_ms) < IDLE_OFF_MS;
-  if (want_on != motor_on) { motor_on = want_on; ... }
-  if (motor_on) { motor.loopFOC(); motor.move(C.w_ramp); }
+  static bool had_nonzero = false;
+  static bool field_on = false;
+  const bool fight_wants = had_nonzero && (millis() - nonzero_ms) < IDLE_OFF_MS;
+  const bool stand_wants = (stand_mode != proto::MODE_FIGHT);
+  const bool want_on = fight_wants || stand_wants;
+  if (want_on != field_on) { field_on = want_on; ... }
```

**Изменение поведения, которое надо знать:** появилось условие
`had_nonzero`. Раньше после сброса поле включалось само на `IDLE_OFF_MS`
(4 секунды) при `VOLTAGE_LIMIT = 2.5 В` — поле вставало на нулевой угол и
притягивало ротор. В `АНТИЗУБЦАХ` этот рывок измерен: **−19.2° за две
секунды**. На валу камера, а сброс происходит при каждой заливке прошивки и
при каждом включении питания.

Теперь поле включается **только после первой ненулевой уставки**. Плюс
`motor.disable()` сразу после `motor.init()`: библиотека в конце своего
`init()` зовёт `enable()` сама (`BLDCMotor.cpp:108`).

Для боевой работы это ничего не меняет: телефон всё равно начинает с уставок,
и первая ненулевая включает поле как прежде. Меняется только поведение платы
**без телефона** — она больше не греет обмотки просто так.

### 1.3. Телеметрия: угол может идти сырым

```diff
+  if (stand_raw) return sensor.getAngle();
```

В боевом режиме `stand_raw` всегда `false` (телефон команду не шлёт, а
таймаут гасит её через 2 с). Медиана работает как работала.

### 1.4. Ответ на запрос

```diff
-  sendTelemetry(seq);
+  if (stand_diag) sendDiag(seq); else sendTelemetry(seq);
```

То же самое: в боевом режиме `stand_diag` всегда `false`.

## 2. Что добавилось и боевого пути НЕ касается

- **Второй тракт энкодера** — аппаратный захват TIM2 на PA15
  (`captureBegin`, `captureRead`). Читается только внутри `sendDiag`, то есть
  в бою не вызывается ни разу. TIM2 свободен: `TIMER_TONE = TIM6`,
  `TIMER_SERVO = TIM7`, а привод для 6-PWM берёт advanced-таймеры.
- **Приём команд** `0xC3` и три предохранителя.
- **Диагностический пакет** `0x5C` с сырыми величинами обоих трактов.

---

## 3. Чем рискуем при заливке

| риск | оценка | что делать |
|---|---|---|
| **Рывок вала при сбросе** | был всегда, теперь **устранён** — но сама заливка идёт на СТАРОЙ прошивке, где он есть | убрать людей от вала на время заливки |
| Заливка не верифицируется | Mass Storage возвращает код `cp` | смотреть `FAIL.TXT`, затем проверить связь и различитель прошивки |
| Путь возврата один | openocd упирается в права USB | поставить udev-правило ДО заливки (см. `stm/ВОЗВРАТ.md`) |
| Ресинхронизация приёма | ухудшение теоретически возможно, практически незаметно | наблюдать `crc_err_count` в первых прогонах |
| Флеш и ОЗУ | 35% и 12% | запас большой |

---

## 4. Как проверить, что залилось именно новое

Формат телеметрии одинаков, версия протокола нулевая в обеих, идентификатора
сборки нет. **«Плата отвечает 20/20» не отличает прошивки.**

Различитель — команда `0xC3`: новая отвечает, старая игнорирует. Готовая
проверка в `stm/ВОЗВРАТ.md`, команда выбрана безвредная (выключение
диагностики).

---

## 5. Что этой заливкой ещё НЕ решается

- **Полоса замера.** `CMD_RAW` отключает медиану, и это даёт полосу до
  ~100 Гц вместо ~5 Гц. Но проверить это можно только после заливки.
- **Разборщика DIAG-потока нет.** Пакеты будут приходить, а считать по ним
  метрики пока нечем.
- **Скрипта управления стендом нет.** Команды придётся слать вручную.
- **Замкнутого контура нет** и в этой версии: `velocity_openloop` как был.
  Сравнение `closed_loop(old/new)` по-прежнему упирается в то, что замыкать
  нечего.
