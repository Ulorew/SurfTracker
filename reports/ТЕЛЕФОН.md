# Телефон: что измерено и что из этого следует

Сводный отчёт. Заменяет `ТЕЛЕФОН_ЗАМЕРЫ.md` и `ТЕЛЕФОН_ХУДШИЙ_СЛУЧАЙ.md`.

**Устройство:** Redmi Note 14 Pro 5G (24090RA29G), Android 14 / SDK 34,
HyperOS OS1.0.10.0, MT6878 (Dimensity 7300-Ultra), 4×A78 2.5 ГГц + 4×A55
2.0 ГГц, arm64-v8a.

---

## Итог одной таблицей

| вопрос | ответ |
|---|---|
| Модель считает на телефоне то же, что на ноутбуке? | **Да.** После NMS 63 рамки, смещение центра 17.3 px из 640 (6.2% размера рамки) |
| 4K-анализ доступен? | **Да.** LEVEL_3, все пять комбинаций потоков, YUV 4080×3060 со stall 0 нс |
| 3 Гц инференса под записью 4K держится? | **Да, от батареи — все 15 минут.** Такт p95 250 мс против бюджета 333 |
| 4 Гц? | **На границе.** p95 такта 256 мс при периоде 250 — медиана проходит, хвост нет |
| Сколько стоит анализ записи? | **1.3 кадра записи** на каждый кадр анализа: 30.1 → 26.4 fps при 3 Гц |
| Цена чехла? | **Ноль** (3 мс при разбросе между минутами 10 мс) |
| Предел? | **~46 °C по батарее.** После него скорость падает втрое разом |

**Рекомендация: 3 Гц, анализ по требованию, без чехла (он не важен), по
возможности не на зарядке.**

## 1. Инструменты

adb 37.0.1, JDK 21, Android SDK build-tools 35 — локально, без sudo, в
`~/Android`. Один `source ~/Android/env.sh` кладёт всё в PATH.

Gradle не заводился намеренно: APK собирается четырьмя вызовами SDK
(`aapt2` → `javac` → `d8` → `apksigner`), без разрешения зависимостей из сети
на каждую сборку. Три приложения: `android/verify` (сверка и скорость),
`android/camprobe` (разведка камеры), `android/camfps` (потоки, запись,
худший случай).

Два ограничения HyperOS, на которые ушло время: `pm grant` заблокирован
(shell без `GRANT_RUNTIME_PERMISSIONS`) — разрешения запрашивает само
приложение, один тап; установка каждого нового пакета требует подтверждения
на экране.

## 2. Камера: что умеет

| | значение |
|---|---|
| INFO_SUPPORTED_HARDWARE_LEVEL | **LEVEL_3** (обе камеры) |
| макс YUV_420_888 (тыл) | **4080×3060** |
| `getOutputStallDuration` на нём | **0 нс** |
| мин. длительность кадра | 33.3 мс (потолок 30 fps) |
| обязательных комбинаций потоков | 62 |

LEVEL_3 подтверждён устройством — дыра ресёрча закрыта. Все пять кандидатов
`isSessionConfigurationSupported` поддержаны, включая главный:
**PRIV 1080p + PRIV 4K + YUV max**.

## 3. Сверка инференса

Заявленный тикетом допуск 1e-5 обоснован тем, что «интерпретатор тот же».
**Посылка неверна:** на ноутбуке x86-64 и на телефоне arm64 работают разные
сборки с разными ядрами XNNPACK. Проверено замером, а не рассуждением:
входной тензор на телефоне совпал с ноутбучным побитово (px0 = ff98a3a9 =
RGB(152,163,169); сумма 1.2 млн значений 702964.31 против 702964.38 — разница
порядка накопления), а выходы разошлись на 2e-3.

После NMS — то, что получает трекер:

| | |
|---|---|
| рамок сопоставлено по IoU | 63, без пары 0 |
| разница в числе рамок | 0 |
| худшее смещение центра | 17.3 px из 640 = **6.2% размера рамки** |
| худшее расхождение уверенности | 0.020 |

Режим `phone_pack.py compare-nms` с допуском в долях размера рамки (10% —
вшестеро строже критерия «та же цель» самого трекера).

## 4. Скорость инференса

APK, не adb-бинарь. 30 прогревочных + 200 замеряемых, чистый `interp.run()`.

| модель | потоки | p50 | p95 |
|---|---|---|---|
| **w8a32** | **1** | **135.4** | **142.9** |
| w8a32 | 2 | 138.7 | 143.6 |
| w8a32 | 4 | 141.6 | 152.3 |
| w8a32, закреплён на A78 | 1 | 135.4 | 141.2 |
| fp32 | 1 | 231.2 | 240.5 |

**Потоки не дают ничего**, и это проверено на уровне механизма: XNNPACK
создаёт 4 потока, но один несёт 95.5% CPU, остальные три по 5.8% — граф не
распараллеливается. Закрепление на больших ядрах не меняет ничего; процесс и
так в cpuset `/top-app`. **fp32 вдвое медленнее** — квантованная сборка
оправдана и по скорости, не только по размеру (3.0 против 10.6 МБ).

## 5. Поток анализа: цена для записи

Проверено подсчётом кадров в самих файлах записи, а не счётчиком тактов.

| режим анализа | YUV fps | **запись 4K** | макс. разрыв записи |
|---|---|---|---|
| без анализа | — | **30.07** | 33.8 мс |
| по требованию, 3 Гц | 3.03 | **26.36** | 115 мс |
| по требованию, 4 Гц | 4.01 | 24.94 | 135 мс |
| по требованию, 5 Гц | 5.06 | 23.64 | 202 мс |
| в каждом такте | 20.7 | 20.93 | 67.6 мс |

**Поток анализа обязан быть по требованию, а не в повторяющемся запросе** —
правка бесплатная, выигрыш +5.4 fps записи. Цена одного полноразмерного
кадра анализа — примерно **1.3 кадра записи**, в диапазоне 3–5 Гц линейно.

Икота растёт нелинейно: между 3 и 4 Гц +20 мс, между 4 и 5 — скачок +67.
Граница заметной икоты лежит между 4 и 5 Гц.

Путь снимков: 3 JPEG/с при записи 4K держатся ровно (3.02/с), запись не
прерывается, но максимальный разрыв растёт с 67.6 до 118.5 мс.

## 6. Худший случай: четыре прогона по 15 минут

Запись 4K + YUV 4080×3060 по требованию + инференс на кропе 640×640.
**Кроп:** 640×640 из полного YUV 4080×3060, угол (1720, 1210), центр кадра.
Конвертируется только окно — 0.41 млн пикселей из 12.5 млн.

| | старый (YUV каждым тактом) | 1: чехол, USB | 2: без чехла, USB | **3: без чехла, батарея** |
|---|---|---|---|---|
| старт | 45 °C / 89% | 35.0 °C / 33% | 37.0 °C / 29% | **35.0 °C / 41%** |
| YUV | 20.85 fps | 3.00 | 3.01 | **3.00** |
| запись, по файлу | 20.93 fps | 26.12 | 26.59 | **26.13** |
| макс. разрыв записи | 76 мс | 207 | 115 | **101** |
| инференс p50 | 310.2 | 182.1 | 185.4 | **186.2** |
| кроп p50 / p95 | **не считался** | 27.0 / 78.5 | 27.4 / 90.2 | **25.8 / 30.9** |
| **такт p95, устойчивый участок** | не мерился | ~240 | ~242 | **250 (весь прогон)** |
| **обвал** | — | **14-я мин** | **12-я мин** | **не было** |
| 46 °C достигнуто | — | ~13-я мин | 11-я мин | 15-я мин |
| заряд | 89 → 84% | 33 → 28% | 29 → 25% | 41 → 34% |

Поминутный такт p95 от батареи: 258, 239, 257, 246, 243, 250, 243, 249, 245,
256, 247, 249, 254, 247, 258 — ровная полка без выбросов.

### Предел — не бюджет такта, а температура

Обвал воспроизводится: скорость падает **втрое разом**, а не постепенно, и
частота анализа проседает с 3.0 до 2.0 Гц. Происходит это через минуту после
того, как батарея достигает 46.0 °C.

Зарядка до порога **разгоняет** (0.82 против 0.73 °C/мин), но потолок тот же:
прогон от батареи тоже дошёл до 46.0 °C — на 15-й минуте, и на этом
закончился. Обвал пришёлся бы на 16-ю, которой не случилось.

Цена чехла — **ноль**: 3 мс по p50 при разбросе между минутами 10 мс.

### Приборы, которым нельзя верить

- `getCurrentThermalStatus` во всех прогонах показывал **0** (троттлинга нет)
  при падении скорости втрое.
- `getThermalHeadroom` в прогоне БЕЗ обвала был самым высоким из всех
  (1.210), а в прогонах с обвалом — 1.149 и 1.159. Как предиктор бесполезен.
- Доступа к тепловым зонам SoC нет (`/sys/class/thermal` закрыт для shell),
  поэтому вся температура здесь — температура батареи.

## 7. Выбор частоты

| | 3 Гц | 4 Гц |
|---|---|---|
| период такта | 333 мс | **250 мс** |
| такт p50 | 209–212 | 211 |
| **такт p95** | **240–250 — запас 25–28%** | **256 — превышение 2%** |
| запись | 26.1–26.6 fps | 24.94 fps |
| макс. разрыв записи | 101–207 мс | 135 мс |

Инференс от частоты не зависит (183 против 186 мс) — меняется доля периода,
которую он занимает: 63% на 3 Гц, 85% по медиане и 102% по хвосту на 4 Гц.

**3 Гц**: не потому что 4 невозможны, а потому что на 3 есть запас, который
съест прогрев, а на 4 запаса нет уже на холодном аппарате.

## 8. Дефекты, найденные в собственных замерах

Перечислены, чтобы не всплыли позже как чужие.

1. **Сортировка якорей по уверенности** сопоставляла РАЗНЫЕ якоря при разнице
   в их числе на единицу: «медиана расхождения 152 px» там, где после NMS
   1.7 px.
2. **Порог сопоставления рамок в долях кадра** объявлял непарной крупную
   рамку 280 px, чей центр сместился на 17 px. Заменён на IoU.
3. **Сборщик мусора собирал `SurfaceTexture` и `ImageReader`** посреди
   сессии: держался только `Surface`, а он их не удерживает. Захват вставал
   ровно через 9 секунд, и это выглядело как обрыв записи. Три моих
   объяснения подряд (YUV не тянет, гаснет экран, плохие параметры записи)
   были неверны; ответ дал только полный logcat.
4. **В первом худшем случае кропа не было вообще** — поток инференса гонял
   нулевой буфер и ни разу не читал кадр камеры. Числа 310/447 мс были
   временем интерпретатора без подготовки кадра.
5. **«Главный подозреваемый — зарядка»** — верно наполовину: порог тот же,
   зарядка лишь разгоняет до него.

## 9. Что осталось

1. **Прогон 25 минут от батареи** — закрывает вопрос о пороге: обвал на 16-й
   минуте подтвердит 46 °C окончательно.
2. **GPU-делегат** — не пробовался вовсе. Разгрузил бы CPU, который делит
   кристалл с кодировщиком.
3. **Причина обвала помимо температуры** — второй кандидат — размер файла
   записи (5.2 ГБ к 14-й минуте, таблица сэмплов MPEG4Writer растёт).
   Разделяется прогоном с перезапуском записи каждые 5 минут.
4. **Анализ 1080p по требованию** — не мерился; вероятно, почти не отнимает у
   записи. Вопрос плотности пикселей на дальнем парусе против гладкости.

## 10. Погашенный экран замедляет инференс в 3.7 раза

Найдено 11 августа при постройке контура слежения, стоило пяти неверных
версий подряд.

| состояние | инференс, yolo11n 640, w8a32 |
|---|---|
| экран погашен (доза) | **526 мс** |
| экран горит | **142 мс** |

Андроид переселяет фоновые приложения на малые ядра. Приложение при этом
работает, wake lock держится, поток не замирает — просто всё считается втрое
медленнее.

**Признак, по которому это узнаётся: время НЕ ЗАВИСИТ ни от чего.** В дозе
одинаково выходило при одном и четырёх потоках, с XNNPACK и без, на модели с
пятью строками выхода и с восемьюдесятью четырьмя, при потоке камеры 4080 и
1920, и — решающее — при полном отсутствии камеры. Постоянное время при любых
настройках вычислений означает, что упираемся не в вычисления.

Перебор неверных версий занял больше часа: XNNPACK, число потоков, размер
выхода модели, разрешение камеры, повторяющийся запрос вместо съёмки по
требованию. Все пять давали одинаковые 525-555 мс, и именно это одинаковство
было ответом, а не шумом.

**Правило для всех замеров на устройстве: экран обязан гореть, а активность —
быть на переднем плане.** Методы `setTurnScreenOn` и `setShowWhenLocked`
помогают только если активность стартует при уже разбуженном устройстве;
надёжнее выставить тайм-аут экрана вручную на время прогона.
