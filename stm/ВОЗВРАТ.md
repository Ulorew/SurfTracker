# Возврат к рабочей прошивке: что делать, если стало хуже

Проверено 21 августа 2026 на машине `lm`. Здесь только то, что **проверено
существованием файлов и утилит**; невыполненное помечено явно.

---

## Коротко

```bash
cd ~/Projects/SurfTracker
./stm/build.sh phone_link --прошить      # соберёт из исходников и зальёт
```

Это основной путь. Он собирает прошивку заново из дерева, поэтому годится
только если **дерево в нужном состоянии**. Для отката к состоянию до реформы:

```bash
git stash                                 # или git checkout <нужный коммит> -- stm/
./stm/build.sh phone_link --прошить
```

## Чем именно заливается

`arduino-cli` для этой платы по умолчанию берёт **Mass Storage**: копирует
`.bin` на том ST-LINK, смонтированный как `/media/ulorew/DIS_G431CB`.

```
Disco.menu.upload_method.MassStorage      <- первый в списке, то есть умолчание
Disco.menu.upload_method.MassStorage.upload.tool=massStorageCopy
```

**Этот путь ничего не верифицирует.** `massStorageCopy.sh` возвращает код
`cp`, то есть успех означает лишь, что байты приняла файловая заглушка
ST-LINK. Обратное тоже верно: после программирования том переподключается, и
`cp` может вернуть ошибку ввода-вывода при УДАЧНОЙ прошивке.

После заливки этим путём **смотреть `FAIL.TXT`** на томе:

```bash
ls /media/ulorew/DIS_G431CB/          # FAIL.TXT быть не должно
cat /media/ulorew/DIS_G431CB/FAIL.TXT 2>/dev/null
```

## Ручная заливка, если `arduino-cli` недоступен

```bash
cp stm/backup/phone_link_21.08/phone_link.ino.bin /media/ulorew/DIS_G431CB/
sync
```

Файл 46 КБ, на томе свободно 148 КБ — влезает. Проверено, что том
смонтирован на запись.

## Путь С ВЕРИФИКАЦИЕЙ — openocd, и он СЕЙЧАС НЕ РАБОТАЕТ

Штатный рецепт ядра программирует `.elf` и проверяет записанное:

```
program {...}.elf verify reset exit
```

`openocd` установлен (`0.12.0`, в комплекте ядра), но при попытке
подключиться выдаёт:

```
Error: libusb_open() failed with LIBUSB_ERROR_ACCESS
```

**Причина:** нет правил udev для ST-LINK. Устройство `/dev/bus/usb/001/009`
принадлежит `root:root` с правами `crw-rw-r--`, обычный пользователь открыть
его не может. В `/etc/udev/rules.d/` правил для `0483:374b` нет.

**Лечение (нужен sudo, требует пароль — выполнить владельцу):**

```bash
sudo cp ~/.arduino15/packages/STMicroelectronics/tools/xpack-openocd/*/openocd/contrib/60-openocd.rules \
        /etc/udev/rules.d/
sudo udevadm control --reload-rules && sudo udevadm trigger
# переподключить USB-кабель платы
```

Правило штатное, из комплекта openocd, и покрывает наш идентификатор:
`ATTRS{idVendor}=="0483", ATTRS{idProduct}=="374b", MODE="666"`.

Проверка, что заработало (**запись не делается**, только опрос):

```bash
OCD=$(ls ~/.arduino15/packages/STMicroelectronics/tools/xpack-openocd/*/bin/openocd | head -1)
"$OCD" -f interface/stlink.cfg -f target/stm32g4x.cfg -c "init; targets; shutdown"
```

**Пока это не сделано, путей заливки ровно один — Mass Storage без
верификации.** Это стоит починить ДО первой заливки, а не после: если
неверифицированная запись пройдёт наполовину, второго способа зайти не будет.

## Чего НЕ существует на этой плате

- **DFU/BOOT0.** Вывод BOOT0 на B-G431B-ESC1 совмещён с **PB8** — тем самым
  проводом, которым подключён энкодер. Загрузчик по UART сидит на пинах,
  занятых силовой частью.
- **STM32CubeProgrammer.** `STM32_Programmer_CLI` не установлен, поэтому все
  методы `swdMethod`, `dfuMethod`, `serialMethod`, `jlinkMethod` из
  `boards.txt` нерабочие.

## Что лежит в бэкапе и чему он соответствует

`stm/backup/phone_link_21.08/` — `bin`, `elf`, `hex`, `map`, собраны из
коммита `4b9dd8d`.

**Это артефакт сборки, а не снимок флеша.** Соответствие содержимому чипа не
проверялось и офлайн непроверяемо: инструментов чтения флеша нет (openocd мог
бы, но упирается в те же права). То есть бэкап гарантирует «из этого дерева
собирается ровно этот двоичный файл», а не «на плате лежит ровно он».

`.elf` и `.hex` держатся в репозитории намеренно — рецепт openocd
программирует именно `.elf`, и без него путь с верификацией остался бы без
файла на любой свежей машине.

## Как отличить, какая прошивка на плате

Формат телеметрии у старой и новой одинаков, поле версии равно нулю в обеих,
идентификатора сборки в протоколе нет. **«Плата отвечает 20/20» не отличает
их.**

Различитель есть: новая прошивка принимает команду `0xC3`. Старая её
проигнорирует — накопит 11 байт, не найдёт `MAGIC_REQ`, отбросит.

```bash
cd ~/Projects/SurfTracker
.venv/bin/python - <<'EOF'
import sys, time, socket
sys.path.insert(0, "tools/link")
from proto_v2 import *
s = socket.socket(socket.AF_BLUETOOTH, socket.SOCK_STREAM, socket.BTPROTO_RFCOMM)
s.settimeout(10); s.connect(("38:18:2B:30:7D:86", 1))
s.sendall(build_cmd(1, CMD_DIAG, 0.0))      # выключить диагностику: безвредно
time.sleep(0.3)
d = s.recv(64); s.close()
print("ответ:", d.hex(" ") if d else "нет")
print("НОВАЯ прошивка" if d else "старая прошивка (команду не поняла)")
EOF
```

Команда выбрана безвредная: выключение диагностики. Даже если прошивка новая
и режим уже выключен, ничего не изменится.
